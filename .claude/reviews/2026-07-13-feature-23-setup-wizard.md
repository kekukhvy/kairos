## Findings

### F1 — Dashboard "Create Task" CTA passes a no-op refresh, leaving stat cards stale
- Source: architecture-reviewer
- File: `kairos-admin/src/main/java/dev/kairos/admin/feature/dashboard/DashboardView.java`:135
- Severity (as reported): must-fix
- Detail: `openWizard()` does `new SetupWizard(..., () -> { }).open()` — an empty `Runnable` for the on-success callback. `TaskView` correctly passes `this::refresh`, but the Dashboard passes a no-op. AC #8 ("on success the wizard notifies, closes, and the originating view refreshes") and the spec both require the originating view to refresh. After creating a task via the Dashboard CTA, the stat cards (active/total tasks, active/total schedules) stay stale until a full page reload, because `render()` only re-lays-out from the already-cached `stats`; it never re-calls `dashboardService.load()`.
- Proposed fix: pass a callback that reloads stats and re-renders, e.g. extract `private void refreshStats() { stats = dashboardService.load(); render(); }` and pass `this::refreshStats` as the on-success runnable.
- Verdict: VALID (must-fix)
- Reason: Confirmed by reading `DashboardView.java` — `stats` (line 61) is assigned exactly once, in the constructor (line 89: `stats = dashboardService.load()`); `render()` (line 138) only re-lays-out from the cached field and never calls `dashboardService.load()` again. `openWizard()` (line 134-136) passes `() -> { }` as `onSuccess`. So after creating a task via the Dashboard CTA, the stat cards are stale until a full page reload — this directly contradicts spec AC #8 ("on success... the originating view refreshes"), which `TaskView.openWizard()` (line 219, `this::refresh`) correctly honors. Cost: a real, user-visible correctness bug on the primary CTA the wizard spec calls out as its main launch point.
- Severity: must-fix
- **Outcome: fixed** — `DashboardView.openWizard()` now passes `this::refreshStats`; added `private void refreshStats() { stats = dashboardService.load(); render(); }` so the Dashboard CTA reloads stats+cards on wizard success, matching `TaskView`'s `this::refresh`.

### F2 — Wizard open triggers an N+1 API fan-out with no error handling (silent failure on open)
- Source: code-review (high) — verifier: CONFIRMED
- File: `kairos-admin/src/main/java/dev/kairos/admin/feature/wizard/SetupWizard.java`:57-58 (and launch points `DashboardView.java`:135, `TaskView.java`:219)
- Severity (as reported): must-fix
- Detail: The `SetupWizard` constructor eagerly makes synchronous REST calls: `destinationService.list()`, `taskService.list()`, and `existingSchedules(...)` → `scheduleService.listForTasks(...)`, which loops one paged request **per task** (`ScheduleService.listForTasks` → `listByTask` → `fetchPage`). So opening the wizard on a system with N tasks does 2 + N(+pages) synchronous round-trips inside the button-click handler. Worse, `DashboardView.openWizard()` / `TaskView.openWizard()` call `new SetupWizard(...).open()` directly — NOT through `ViewActions.execute` — so if any of those list calls throws (API down/timeout/`RestClientResponseException`), the exception propagates out of the click listener: no dialog opens and no `Notifications.error` shows. This bypasses the app's own uniform error-handling convention (`ViewActions`) and is a worse failure mode than the rest of the UI.
- Proposed fix: (a) route the wizard-open path through `ViewActions.execute` (or a small try/catch that shows `Notifications.error` and logs) so a failed load notifies instead of silently doing nothing; (b) the N+1 is design-level (the list API is task-scoped) — at minimum avoid the per-task schedule fan-out for the "existing schedule shape" picker if it isn't essential, or defer/lazy-load it. The unhandled-exception fix is the low-effort, high-value half.
- Verdict: split — (a) unhandled-exception-on-open: VALID (must-fix). (b) N+1 fan-out: NEEDS-HUMAN — is fixing the per-task schedule fan-out in scope for this slice, or deferred alongside the atomic multi-create endpoint the spec already defers?
- Reason: Confirmed both sub-claims by reading the code. `SetupWizard`'s constructor (lines 52-58) calls `destinationService.list()`, `taskService.list()`, and `existingSchedules(...)` → `ScheduleService.listForTasks` (`ScheduleService.java`:100-107) synchronously with **no try/catch anywhere in the call chain**; `listForTasks` loops `listByTask` once per task id, and `listByTask` (lines 59-77) itself pages via `fetchPage`. `DashboardView.openWizard()` (line 135) and `TaskView.openWizard()` (line 219) both call `new SetupWizard(...).open()` directly, not through `ViewActions.execute`/`ViewActions.executeAndRefresh` (`ViewActions.java`) — the app's own established convention for surfacing API failures via `Notifications.error` + log. If any of those three list calls throws, the exception propagates out of the button click listener uncaught: no dialog, no notification, no log — a materially worse failure mode than every other view in the codebase. This part is a clear, low-effort convention violation — VALID must-fix. The N+1 fan-out itself is real (confirmed: one paged HTTP round-trip per task, inside a modal-open path) but is a design/performance tradeoff, not a correctness bug, and the spec explicitly designs the wizard around the existing task-scoped list APIs with no new atomic/batch endpoint (`doc/specs/setup-wizard.md` "Out" section) — deciding whether to reshape or defer this is a scope call for the user, not something to unilaterally mark must-fix or drop.
- Severity: must-fix (part a only; part b is NEEDS-HUMAN, not scored as must-fix/suggestion)
- **Outcome: fixed** — (a) `DashboardView.openWizard()` and `TaskView.openWizard()` now wrap `new SetupWizard(...).open()` in a try/catch that logs and shows `Notifications.error(WizardText.NOTIFY_OPEN_FAILED)` on a `RuntimeException`. (b) N+1 fan-out resolved by user-approved design change: the Schedule step no longer has a "select existing" mode at all (it always creates a new schedule for the new task), so `SetupWizard` no longer calls `scheduleService.listForTasks(...)` or `taskService.list()` at all — the per-task schedule fan-out is gone entirely, not just error-wrapped. See FIX A / the WizardMode/ScheduleStep changes below.

### F3 — Retry after a schedule-create failure creates a DUPLICATE schedule (no idempotency guard on the schedule step)
- Source: code-review (high) — verifier: CONFIRMED
- File: `kairos-admin/src/main/java/dev/kairos/admin/feature/wizard/WizardCommit.java`:67-72
- Severity (as reported): must-fix (spec-acknowledged gap, but a real duplicate-creation defect)
- Detail: `resolveDestination` (line 47) and `resolveTask` (line 59) both short-circuit on a captured non-null id, so a repeated Finish skips them. `resolveSchedule` has NO such guard — it only checks `scheduleMode() == CREATE_NEW`, and `WizardDraft` has no `scheduleId`/"created" flag. `SetupWizard.finish()` catches a commit failure, notifies, and leaves the wizard open with Finish live. If destination+task succeed but the schedule POST fails (API 5xx, or the POST actually succeeded server-side but the response was lost in transit), a second Finish re-runs `resolveSchedule` and POSTs a **second** schedule for the same task. The spec's AC #7 only promises no-duplicate for destination/task and marks schedule create "terminal", so this is a spec-acknowledged gap — but the spec's own retry rationale ("re-runs only the failed/remaining steps and does not duplicate what already succeeded") is not honored for the terminal schedule step, and a duplicate schedule on a transient-failure retry is a genuine defect.
- Proposed fix: capture a "schedule created" flag (or the created schedule id) on `WizardDraft` and guard `resolveSchedule` on it, exactly like destination/task — so a retry after a schedule failure that actually persisted server-side won't double-create. (If truly desired to stay "terminal", at least document the duplicate-on-retry window; but a guard is cheap and consistent.)
- Verdict: VALID (must-fix)
- Reason: Confirmed by reading `WizardCommit.java`: `resolveDestination` (line 46-56) and `resolveTask` (line 58-65) both guard on a captured id (`if (draft.destinationId() != null) return;` / `if (draft.taskId() != null) return;`), but `resolveSchedule` (line 67-72) only checks `draft.scheduleMode() != WizardMode.CREATE_NEW` — there is no captured-schedule-id or "created" flag on `WizardDraft.java` (confirmed no such field exists) to short-circuit a repeat. Spec AC #7 literally only promises no-duplicate for "destination/task", so the wizard technically satisfies its own AC as worded — but the spec's own commit-sequence rationale (`doc/specs/setup-wizard.md` line 128-132: "the guards (`== null`) mean a repeated Finish skips what already succeeded and retries only the failed/remaining call") describes an idempotent-retry intent that is silently *not* honored for the terminal schedule step. This is a real, reachable failure mode (network blip/timeout after the POST actually landed server-side, or any transient 5xx after success) that produces a genuine duplicate schedule for the same task on the very next Finish click — not merely a spec-scoping technicality. The fix is cheap and mirrors the existing pattern two lines above it, so there's no good reason to leave the asymmetry in.
- Severity: must-fix
- **Outcome: fixed** — added `WizardDraft.scheduleCreated`/`markScheduleCreated()`, and `WizardCommit.resolveSchedule` now guards `if (draft.scheduleCreated()) return;` before creating, mirroring `resolveDestination`/`resolveTask`, then calls `draft.markScheduleCreated()` after the POST succeeds. Added `WizardCommitTest.commit_retryAfterScheduleCreationFails_doesNotDuplicateScheduleOnRetry`: first schedule-create attempt throws, a retry creates it exactly once more (2 total calls, not 3), and a third `execute()` call makes no further schedule-creator calls. All 12 `WizardCommitTest` cases pass.

### F4 — After a partial failure, editing an already-committed step is silently discarded on retry
- Source: code-review (high) — verifier: PLAUSIBLE
- File: `kairos-admin/src/main/java/dev/kairos/admin/feature/wizard/WizardCommit.java`:47,59 (+ `WizardDraft` never resets captured ids; `SetupWizard.goBack()`)
- Severity (as reported): suggestion
- Detail: After destination is created but task create fails (e.g. 409), the user may go Back to the Destination step, edit it, and click Finish again. But `draft.destinationId` is still populated, so `resolveDestination` returns early — the edited destination is never created and the already-created (wrong) destination id is reused for the task. Nothing resets captured ids on Back, and the discard is silent (no indication). This is largely WORKING AS SPECIFIED (the spec designs skip-already-created retry and puts wizard-editing out of scope), so it is a suggestion, not a must-fix — but the spec did not weigh the "correct a wrongly-created entity" case, and the silent discard is a real UX gap.
- Proposed fix: on a commit failure, surface which entities were already created (e.g. in the error notification or a small summary line), and/or when the user navigates Back to an already-committed step, either lock it (read-only, "already created") or clear the captured id so an edit re-creates. Minimal version: make the already-created state visible so the discard isn't silent.
- Verdict: VALID (suggestion)
- Reason: Confirmed by reading `WizardStepState.back()` (`WizardStepState.java` lines 48-53) — it only decrements the step index, touching nothing on `WizardDraft`; and `WizardCommit.resolveDestination`/`resolveTask` (lines 46-65) both return early once `draft.destinationId()`/`draft.taskId()` is non-null. So after destination succeeds and task fails, going Back to Destination and editing its fields, then Finish, silently reuses the *original* (unedited) destination id — the edit is discarded with no indication. This is largely the natural consequence of two deliberate spec decisions (`doc/specs/setup-wizard.md`: skip-already-created retry is *designed*; "editing existing entities through the wizard" is explicitly out of scope) rather than an unintended defect, which is why it stays a suggestion, not must-fix — but the spec never actually weighed "user edits an already-committed step to correct a mistake after a *different* step failed," and a silent discard (vs. a locked/labelled step, or at least a hint) is a real, cheap-to-improve UX gap worth a follow-up.
- Severity: suggestion
- **Outcome: no_change_needed** — per triage, left as-is; this follows from the specified idempotent-retry design (skip-already-created on retry) and is a genuine but separate UX follow-up, out of scope for this fix pass.

### F5 — Schedule/task field validation duplicated between the standalone forms and the wizard steps
- Source: architecture-reviewer
- File: `kairos-admin/src/main/java/dev/kairos/admin/feature/wizard/component/ScheduleStep.java`:136-189 (vs `feature/schedule/component/ScheduleForm.java`:210-253); `component/TaskStep.java`:70-77 (vs `TaskForm.java`:144-151)
- Severity (as reported): suggestion
- Detail: `validateRunAt()`, `validateInterval()`, `runAtInstant()`, `selectedZone()`, and `showFieldsForType()` are near-identical between `ScheduleStep` and `ScheduleForm`; `TaskStep.validate()`'s required-field block mirrors `TaskForm.validate()`. A fix to the timezone-fallback, run-at-future, or interval-bounds rule must now be made in two places. The spec scoped shared-validation extraction as "where practical" and deferred it, and the two call sites genuinely diverge in shape (dialog-with-footer vs embedded step, create-vs-edit branching in `ScheduleForm`), so this is a follow-up, not a blocker.
- Proposed fix: extract the four schedule "when"-validation/parsing methods into a small static helper (e.g. `ScheduleFieldValidation` beside `shared/form/FieldValidation`) taking the concrete Vaadin fields as parameters — a couple of static methods, no new interface/base class (KISS). Both `ScheduleForm` and `ScheduleStep` call it. Same, lower-priority, for the task required-field block.
- Verdict: split — schedule half VALID (suggestion); task half INVALID — already thin/shared, no separate rule duplicated
- Reason: Confirmed by reading both files side by side. `ScheduleStep.validateRunAt/validateInterval/runAtInstant/selectedZone` (`ScheduleStep.java` lines 136-189) and `ScheduleForm`'s versions (`ScheduleForm.java` lines 210-253) are **byte-identical** — same field-error messages, same future-check, same UTC fallback and `DateTimeException` catch — a real GUIDELINES §5 DRY violation (a fix to the run-at-future rule or the timezone fallback must be made in two places today). That half is VALID (suggestion) — the spec itself scoped shared-validation extraction as "where practical" and deferred it, and it's a follow-up, not a blocker, so suggestion severity is correct, not must-fix. The task half is different on inspection: `TaskStep.validate()` (lines 70-77) and `TaskForm.validate()` (lines 144-151) are each already thin — every check is a direct call to the shared `FieldValidation.require`/`requirePresent` helper (`shared/form/FieldValidation`, already extracted); the only "duplication" is which fields get validated, and that legitimately differs (`TaskForm` also requires `destinationId`, which `TaskStep` correctly omits because destination is a separate wizard step). There is no duplicated *rule* left to extract on the task side — extracting a two-line sequence of pre-existing shared-helper calls would be churn for churn's sake (KISS/DRY don't apply to a call sequence that isn't itself a rule).
- Severity: suggestion
- **Outcome: fixed (schedule half)** — extracted `validateRunAt`/`validateInterval`/`runAtInstant`/`selectedZone` into new `dev.kairos.admin.feature.schedule.component.ScheduleWhenFields` (plain public static methods over the concrete Vaadin fields, no new interface/base class). Both `ScheduleForm` and `ScheduleStep` now call it; removed the now-unused `DateTimeException`/`ZoneOffset` imports from `ScheduleForm` and the equivalent duplicated methods/imports from `ScheduleStep`. Task half: **no_change_needed**, per the INVALID verdict above — nothing to extract.

### F6 — Step classes expose package-private accessors used only by tests
- Source: architecture-reviewer
- File: `component/TaskStep.java`:98-108, `component/DestinationStep.java`:131-145, `component/ScheduleStep.java`:191-205
- Severity (as reported): suggestion (FYI)
- Detail: Each step exposes package-private field getters (`service()/name()/eventName()`, `existingDestination()/newDestinationId()/...`, `existingSchedule()/type()/runAt()/cronExpression()`) that no production code calls — only the same-package tests. Deliberate test seam; GUIDELINES has no rule against it and the alternatives add machinery for little gain.
- Proposed fix: leave as-is, or add a one-line `// package-private: test-only accessors` comment above each block so a future reader doesn't wonder why `SetupWizard` never calls them.
- Verdict: INVALID — taste-only nit, no GUIDELINES.md rule against test-only package-private accessors
- Reason: Confirmed by reading `TaskStep.java` (lines 98-108: `service()/name()/eventName()` return the raw `TextField`s) and grepping the `feature/wizard` production sources — no production caller exists, only `TaskStepTest.java` (lines 47, 55, 63, 77-78) in the same package. This is a working, deliberate test seam; GUIDELINES.md has no rule forbidding package-private accessors used only by same-package tests, and the finding's own proposed fix ("leave as-is") confirms it isn't asking for a functional change. Adding machinery (an interface, a test-support subclass) would be speculative generality GUIDELINES §4 (KISS) explicitly warns against; a comment is optional polish, not a defect.
- Severity: n/a (INVALID)
- **Outcome: no_change_needed** — INVALID finding, no action taken (per triage).

## Security review

No HIGH or MEDIUM security findings. The change is admin-UI-only, composing the existing `TaskService`/`DestinationService`/`ScheduleService` create endpoints (the API remains the server-side trust boundary). JSON parsing reuses the existing `FieldValidation.parseJson` (Jackson 3, reads to `Object.class`, no default/polymorphic typing → no deserialization-gadget sink). No new endpoint, auth logic, secrets, crypto, file/path/command operations. Vaadin server-side Flow escapes text set via `Span`/labels; no `innerHTML`/`Html` sink introduced. The commit-failure log message contains no PII/secrets.
