           # Kairos — Database Schema (Reference)

> Reference for the key tables based on our design discussion. The schema
> is now **implemented** as Flyway migrations under
> `kairos-api/src/main/resources/db/migration/` — one file per table:
>
> | Migration | Table |
> |---|---|
> | `V1__create_destinations_table.sql` | `destinations` |
> | `V2__create_tasks_table.sql` | `tasks` |
> | `V3__create_retry_policies_table.sql` | `retry_policies` |
> | `V4__create_schedules_table.sql` | `schedules` |
> | `V5__create_executions_table.sql` | `executions` |
> | `V6__create_execution_history_table.sql` | `execution_history` |
> | `V7__tighten_schedules_fixed_interval.sql` | `schedules` (constraint update) |
>
> Verified on a fresh Postgres 16: all seven apply cleanly (6 tables + 7
> FKs), and the CHECK constraints behave (an invalid destination `type` is
> rejected, a `ONCE` schedule without `run_at` is rejected, a `FIXED`
> schedule with `interval_seconds > 86400` is rejected). The migration
> files are the source of truth for exact column names, types, defaults,
> and constraint names; this doc summarizes them and the rationale. Places
> where a decision still hasn't been finalized are marked **TBD**.
>
> Concrete decisions the migrations settled (left implicit in the earlier
> draft):
>
> - UUID primary keys default to `gen_random_uuid()` (pgcrypto, built into
>   Postgres 16) — ids are generated by the DB, not the application.
> - `TIMESTAMPTZ` audit columns (`created_at`, and `updated_at` where
>   present) are `NOT NULL DEFAULT now()`.
> - Enum-like / type columns are guarded by named `CHECK` constraints (see
>   each table below), not Postgres `ENUM` types.

## Entity Overview

```
destinations  1───* tasks  1───* retry_policies
                    tasks  1───* schedules
        tasks/schedules  1───* executions (current)
                executions ──→ execution_history (archive, on completion)
```

- **destinations** — where to deliver (Kafka / SQS / Webhook / RabbitMQ)
- **tasks** — what to deliver and with which retry policy
- **schedules** — when to deliver (one task → many schedules)
- **retry_policies** — retry steps for a task
- **executions** — the current/upcoming plan (hot, small table)
- **execution_history** — archive of all completed runs (append-only)

## destinations

| Column | Type | Notes |
|---|---|---|
| id | VARCHAR(128) PK | human-readable id, e.g. `booking-kafka` |
| type | VARCHAR(32) NOT NULL | `KAFKA` \| `SQS` \| `WEBHOOK` \| `RABBITMQ` |
| config | JSONB NOT NULL | connectivity config; the shape is governed by the per-type schema (see `dev.kairos.common.destination.DestinationConfigSchema` in the `common` module). This is an **application-level contract**, not a DB constraint — the column itself remains a free-form JSON/JSONB. |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |

`CONSTRAINT destinations_type_check CHECK (type IN ('KAFKA', 'SQS',
'WEBHOOK', 'RABBITMQ'))`.

## tasks

| Column | Type | Notes |
|---|---|---|
| id | UUID PK DEFAULT gen_random_uuid() | |
| service | VARCHAR(128) NOT NULL | owning service |
| name | VARCHAR(255) NOT NULL | e.g. `expire-booking` |
| description | TEXT | nullable |
| active | BOOLEAN NOT NULL DEFAULT true | overall kill-switch for the whole task |
| destination_id | VARCHAR(128) NOT NULL FK → destinations (id) | |
| event_name | VARCHAR(255) NOT NULL | machine-readable, versioned event identifier used by the consumer for routing/handler selection (e.g. `booking.expire.v1`); distinct from the human-readable task `name` |
| payload | JSONB | default payload — nullable |
| timeout_ms | INT NOT NULL | delivery timeout |
| supports_retry | BOOLEAN NOT NULL DEFAULT false | if false, retry_policies is not used for this task |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |
| deleted_at | TIMESTAMPTZ NULLABLE | soft delete — if not null, the task is considered deleted |
| last_status | VARCHAR(16) NULLABLE | last run outcome: `SUCCESS` \| `FAILED` \| `DEAD_LETTER`; null until first run |
| last_run_at | TIMESTAMPTZ NULLABLE | when the task last ran; null until first run |
| next_run_at | TIMESTAMPTZ NULLABLE | next planned run; null if nothing scheduled |

`CONSTRAINT tasks_timeout_ms_check CHECK (timeout_ms > 0)`.

`CONSTRAINT tasks_last_status_check CHECK (last_status IS NULL OR last_status
IN ('SUCCESS', 'FAILED', 'DEAD_LETTER'))`.

Soft delete: the row is never physically removed; `deleted_at` is set on
deletion. All normal reads (`GET`, `LIST`) filter `WHERE deleted_at IS NULL`.

Denormalized run summary: `last_status`, `last_run_at`, and `next_run_at`
are a cache maintained by the engine so the task listing can show the last
run outcome, last run time, and next planned run without joining the run
tables. They are **not** the source of truth — `executions` /
`execution_history` remain authoritative for run state and history; these
three columns are a derived convenience for fast listing.

**Indexes:**
- `idx_tasks_active_not_deleted` — partial index on `(created_at)`
  `WHERE deleted_at IS NULL`, supporting the live-rows list query.
- `idx_tasks_destination_id` on `(destination_id)` — FK lookup index.

## retry_policies

Retry steps for a task — a separate table instead of a single JSON blob, so
each step is individually visible and editable.

| Column | Type | Notes |
|---|---|---|
| id | UUID PK DEFAULT gen_random_uuid() | |
| task_id | UUID NOT NULL FK → tasks (id) ON DELETE CASCADE | |
| attempt_number | INT NOT NULL | which attempt this row describes (2, 3, …) |
| delay_seconds | INT NOT NULL | delay before this attempt |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |

Constraints:
- `CONSTRAINT retry_policies_task_attempt_unique UNIQUE (task_id,
  attempt_number)`.
- `CONSTRAINT retry_policies_attempt_number_check CHECK (attempt_number > 0)`.
- `CONSTRAINT retry_policies_delay_seconds_check CHECK (delay_seconds >= 0)`.

Index: `idx_retry_policies_task_id` on `(task_id)` — FK lookup index.

Example (`5s → 30s → Dead Letter`): `attempt_number=2, delay=5`;
`attempt_number=3, delay=30`. If there's no row for the next attempt, the
failure goes to `DEAD_LETTER`.

## schedules

| Column | Type | Notes |
|---|---|---|
| id | UUID PK DEFAULT gen_random_uuid() | |
| task_id | UUID NOT NULL FK → tasks (id) ON DELETE CASCADE | |
| label | VARCHAR(128) NULLABLE | e.g. `weekday-morning`, `weekend` |
| type | VARCHAR(16) NOT NULL | `ONCE` \| `CRON` \| `FIXED` |
| run_at | TIMESTAMPTZ NULLABLE | required for `ONCE` |
| cron_expression | VARCHAR(128) NULLABLE | required for `CRON` |
| interval_seconds | INT NULLABLE | required for `FIXED` |
| timezone | VARCHAR(64) NOT NULL DEFAULT 'UTC' | relevant for `CRON` |
| active | BOOLEAN NOT NULL DEFAULT true | pauses this single rule, independent of `tasks.active` |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |

Constraints:
- `CONSTRAINT schedules_type_check CHECK (type IN ('ONCE', 'CRON',
  'FIXED'))`.
- `CONSTRAINT schedules_type_fields_check` — each type requires **exactly
  its own** "when" field and forbids the others (tightened by `V7`):
    - `ONCE` → `run_at IS NOT NULL`, `cron_expression`/`interval_seconds` null;
    - `CRON` → `cron_expression IS NOT NULL`, `run_at`/`interval_seconds` null;
    - `FIXED` → `interval_seconds IS NOT NULL AND interval_seconds > 0
      AND interval_seconds <= 86400`, `run_at`/`cron_expression` null.

  `V4` originally only enforced `interval_seconds > 0` for `FIXED`. `V7`
  (`V7__tighten_schedules_fixed_interval.sql`) dropped and re-added the
  constraint to add the upper bound of `<= 86400` (one day), keeping the
  DB CHECK consistent with `Schedule.MAX_INTERVAL_SECONDS = 86_400` in the
  domain. An interval longer than a day is a calendar concern and belongs to
  `CRON`, not a plain interval.

  This makes an invalid combination (e.g. `ONCE` without `run_at`, or a
  `FIXED` interval exceeding one day) impossible at the DB level, matching
  the `Schedule.once/cron/fixed(...)` factory-method invariants.

**Indexes:**
- `idx_schedules_task_id` on `(task_id)` — FK lookup index.
- `idx_schedules_active` — partial index on `(active)` `WHERE active =
  true`, for the planner walking live schedules.

## executions (current / hot)

The engine's working table. Stays small — it only holds what's upcoming or
currently in progress.

| Column | Type | Notes |
|---|---|---|
| id | UUID PK DEFAULT gen_random_uuid() | |
| task_id | UUID NOT NULL FK → tasks (id) | |
| schedule_id | UUID NULLABLE FK → schedules (id) | null for ad-hoc runs |
| scheduled_for | TIMESTAMPTZ NOT NULL | when this was supposed to fire |
| next_attempt_at | TIMESTAMPTZ NOT NULL | claim key for `SKIP LOCKED`, moves forward on retry |
| status | VARCHAR(16) NOT NULL DEFAULT 'PENDING' | `PENDING` \| `CLAIMED` \| `RETRYING` |
| attempt | INT NOT NULL DEFAULT 0 | |
| recycle | BOOLEAN NOT NULL DEFAULT false | true for `FIXED` — the row is reused instead of deleted after completion |
| locked_by | VARCHAR(128) NULLABLE | worker id |
| locked_at | TIMESTAMPTZ NULLABLE | for detecting stuck claims |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |

`CONSTRAINT executions_status_check CHECK (status IN ('PENDING', 'CLAIMED',
'RETRYING'))`. Note the FK to `tasks` here is **not** `ON DELETE CASCADE`
(unlike `retry_policies`/`schedules`).

**Indexes:**
- `idx_executions_claim` — partial index on `(next_attempt_at)`
  `WHERE status IN ('PENDING', 'RETRYING')`, the claim-loop index.
- `idx_executions_locked_at` — partial index on `(locked_at)`
  `WHERE status = 'CLAIMED'`, used by the reaper for stuck claims.
- `idx_executions_task_id` on `(task_id)` and `idx_executions_schedule_id`
  on `(schedule_id)` — FK lookup indexes.

`ONCE` / `CRON`: materialized ahead of time (horizon depends on frequency);
the row is archived and removed from here on completion.
`FIXED`: a single row per schedule — on completion it's copied into
`execution_history`, and the same row is updated (`scheduled_for` /
`next_attempt_at` += interval, `status` → `PENDING`) in the same transaction.

## execution_history (archive)

Append-only. The source of truth for all run history, including every tick
of a `FIXED` schedule.

| Column | Type | Notes |
|---|---|---|
| id | UUID PK DEFAULT gen_random_uuid() | |
| task_id | UUID NOT NULL FK → tasks (id) | |
| schedule_id | UUID NULLABLE FK → schedules (id) | |
| source_execution_id | UUID NOT NULL | the `executions.id` this came from (repeats for `FIXED`) — plain UUID, **no FK** (the source row may already be gone) |
| scheduled_for | TIMESTAMPTZ NOT NULL | which tick this was |
| attempt | INT NOT NULL | |
| status | VARCHAR(16) NOT NULL | `SUCCESS` \| `FAILED` \| `DEAD_LETTER` |
| started_at | TIMESTAMPTZ NOT NULL | |
| finished_at | TIMESTAMPTZ NOT NULL | |
| duration_ms | INT NOT NULL | |
| error | TEXT NULLABLE | |
| result | JSONB NULLABLE | **planned for the future, not part of V1** — the service's response |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() | |

`CONSTRAINT execution_history_status_check CHECK (status IN ('SUCCESS',
'FAILED', 'DEAD_LETTER'))`.

**Indexes:**
- `idx_execution_history_task_id` on `(task_id, finished_at DESC)` — the
  per-task, most-recent-first history read.
- `idx_execution_history_schedule_id` on `(schedule_id)` and
  `idx_execution_history_source` on `(source_execution_id)` — lookup indexes.

## JOOQ codegen notes

JSONB columns (`tasks.payload`, `destinations.config`,
`execution_history.result`) are generated as `org.jooq.JSONB` — no forced
type converter is registered. Conversion to/from `String` is handled
explicitly in the mapper layer via `JSONB.valueOf(string)` /
`jsonb.data()`. This avoids a hidden implicit conversion and keeps the
mapping transparent.

## TBD / open questions

- Exact self-healing mechanism for the planner itself (a lock/lease table
  such as `planner_runs`) — not finalized. No such table exists in the
  current migrations (`V1`–`V7`); it will land in a later migration when
  the mechanism is decided.
- Materialization horizon thresholds by frequency — need real numbers
  based on expected load.
- `correlation_id` for the async `result` field — needed once that feature
  is built.
- Maintenance of the denormalized run summary on `tasks` (`last_status`,
  `last_run_at`, `next_run_at`): exactly when/how the engine writes
  `next_run_at` for `FIXED` vs `CRON` schedules, and whether the cache
  update shares a transaction with the `executions` / `execution_history`
  write (or is allowed to drift and be reconciled) — not finalized.
